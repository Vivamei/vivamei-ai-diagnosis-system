# 本地数据库连接指南（MySQL + Redis）

> 适用于在本地用 Docker 跑起 venus-4s 后，用图形客户端连接并查看数据。
> 端口 / 账号来源：`infra/docker-compose.dev.yml`、`config/dev.env`。

---

## 0. 前置：确认容器已启动

先跑 `start-dev.bat`（会自动拉起 Docker 的 MySQL / Redis），或手动：

```bash
docker compose -f infra/docker-compose.dev.yml up -d
```

确认两个容器都在、且 MySQL 是 healthy：

```bash
docker ps
```

应能看到 `venus-mysql`、`venus-redis` 两个容器在运行。

---

## 1. MySQL —— 用 MySQL Workbench 连接

### 连接参数

| 字段 | 值 |
|---|---|
| Connection Name | 随便填，如 `venus-dev` |
| Hostname | `127.0.0.1` |
| Port | `3306` |
| Username | `venus` |
| Password | `devpass` |
| Default Schema | `venus` |

- 数据库名就是 **`venus`**。
- 想看全部库 / 有更高权限，用 root：Username `root`，Password `devroot`。

### 操作步骤（Workbench）

1. 打开 Workbench → 点首页的 **`+`** 新建连接。
2. 按上表填 Hostname / Port / Username。
3. 点 **Store in Vault…** 填密码 `devpass`（或 root 用 `devroot`）。
4. 点 **Test Connection** 测试，成功后 **OK** 保存。
5. 双击该连接进入，左侧 **Schemas** 里展开 `venus` 即可看表。

### 常见坑

- **Hostname 用 `127.0.0.1`，不要用 `localhost`**：Workbench 对 `localhost` 有时走 named pipe / socket，`127.0.0.1` 会强制走 TCP，更稳。
- 连不上先确认 `docker ps` 里 `venus-mysql` 是 healthy（刚启动需等几秒）。
- 端口 3306 被本机已装的 MySQL 占用时，会连到错的实例；先关掉本机 MySQL 服务或改容器端口。

## 2. Redis —— 客户端推荐 + 连接

### 连接参数

| 字段 | 值 |
|---|---|
| Host | `127.0.0.1` |
| Port | `6379` |
| Password | 无（留空） |
| DB | `0` |

对应 `config/dev.env` 里的 `REDIS_URL=redis://localhost:6379/0`。

### 客户端推荐

1. **RedisInsight（首选，官方免费）** — Redis 官方 GUI，功能最全。下载：<https://redis.io/insight/>
   新建连接填 `127.0.0.1:6379`、密码留空、DB 0。看 key / TTL / 编辑值都很直观。
2. **Another Redis Desktop Manager（轻量开源）** — 启动快、占用小，有绿色版免安装。
3. **TablePlus（付费，颜值高）** — 一个软件同时连 MySQL + Redis，省得开两个工具（免费版够日常用）。
4. **redis-cli（命令行，零安装）** — 容器自带：
   ```bash
   docker exec -it venus-redis redis-cli
   ```

## 3. 常用查询：验证码 / 短信频控

> 本地短信走 **Mock**，验证码不真发短信，而是写进 Redis + 打日志。
> 注意 key 里的手机号是 **hash 过的**，不是明文号码。

在 redis-cli（或 GUI 的命令行）里：

```
KEYS sms:*                    # 列出所有短信相关 key
GET  sms:code:<phone_hash>    # 那条 6 位验证码
TTL  sms:code:<phone_hash>    # 验证码剩余有效期（默认 300s）
TTL  sms:send:<phone_hash>    # 60s 发送锁还剩几秒（>0 时再点会被 429）
DEL  sms:send:<phone_hash>    # 【测试用】删掉 60s 锁，立刻可重发
```

用 `KEYS sms:code:*` 先把 key 列出来，再对着取值即可。

### 验证码也能在日志里看

Mock 发码时会打一行日志，在 **API 窗口** 或 `logs/api.log` 里搜：

```
[MOCK SMS] code=xxxxxx
```

## 4. 快速排查「点获取验证码没反应 / 没倒计时」

点一次「获取验证码」后，在 Redis 里看：

- `KEYS sms:*` **有新增** → 后端收到了、Mock 已发码，去 `sms:code:*` 取验证码即可；界面没倒计时多半是刷新丢了前端状态。
- `KEYS sms:*` **没新增** → 请求没到后端，检查 API 窗口（8000 端口）是否起来、前端代理是否正常。
- `TTL sms:send:<hash>` **仍 >0** → 60s 频控锁没过，再点会返回 429「60 秒内只能请求一次」；测试想立刻重发就 `DEL sms:send:<hash>`。

## 5. 数据表清单（MySQL 库 `venus`）

一共 6 张业务表。核心链路：**用户上传照片 → 生成分析任务 → 产出报告 → 预约到店**。

### 表关系一览

```
users ──┬──< photos            (photos.user_id → users.id)
        ├──< analysis_tasks     (analysis_tasks.user_id → users.id)
        └──< bookings           (bookings.user_id → users.id)

photos ───< analysis_tasks      (analysis_tasks.photo_id → photos.id)
analysis_tasks ──1:1── reports  (reports.task_id → analysis_tasks.id，唯一)
analysis_tasks ───< bookings    (bookings.task_id → analysis_tasks.id)

audit_logs                      (独立审计表，不外键关联)
```

### 各表说明

| 表名 | 含义 | 主键 | 关键字段 |
|---|---|---|---|
| `users` | 用户 | `id` (自增) | `phone`(加密) `phone_hash`(唯一) `nickname` `consent_at` `consent_ver` `created_at` `deleted_at` |
| `photos` | 上传照片 | `id` (自增) | `user_id` `oss_key` `width/height/bytes/mime` `moderation_status` `expires_at` `created_at` |
| `analysis_tasks` | 分析任务 | `id` (ULID, 26位字符串) | `user_id` `photo_id` `status` `llm_provider` `error_code/error_message` `started_at/finished_at` `created_at` |
| `reports` | 美学报告 | `id` (自增) | `task_id`(唯一) `stype` `style` `subzone` `struct_` `radar_scores` `optimization` `extra` `full_text` `moderation_status` |
| `bookings` | 预约到店 | `id` (自增) | `user_id` `task_id` `name` `phone`(加密) `phone_hash` `store_code` `appointment_at` `status` `source` |
| `audit_logs` | 审计日志 | `id` (自增) | `actor_id` `actor_ip` `action` `target_type` `target_id` `meta`(JSON) `created_at` |

### 枚举值

- `photos.moderation_status`：`pending` / `passed` / `rejected`
- `analysis_tasks.status`：`queued` / `streaming` / `done` / `failed` / `moderated_out`
- `reports.moderation_status`：`pending` / `passed` / `rejected`
- `bookings.status`：`new` / `contacted` / `arrived` / `closed`

### ⚠️ 手机号是加密的，不能直接按明文查

- `users.phone` / `bookings.phone` 是 **AES-GCM 密文**，SELECT 出来是乱码，不可读。
- `phone_hash` 是 **HMAC-SHA256**，只能用来「按号码定位」，也看不出原始号码。
- 想按某个手机号查用户，需要用后端同款算法先算出 `phone_hash` 再 `WHERE phone_hash = '...'`，无法在 SQL 里直接 `WHERE phone = '138...'`。
- `nickname`、报告内容、预约的 `name` 等非敏感字段是明文，可直接看。

### 常用查询示例

```sql
-- 最近注册的用户（手机号列是密文，看 nickname / 时间即可）
SELECT id, nickname, consent_ver, created_at
FROM users
ORDER BY created_at DESC
LIMIT 20;

-- 最近的分析任务及状态（排查失败任务看 error_code/error_message）
SELECT id, user_id, photo_id, status, llm_provider,
       error_code, created_at, finished_at
FROM analysis_tasks
ORDER BY created_at DESC
LIMIT 20;

-- 只看失败的任务
SELECT id, status, error_code, error_message, created_at
FROM analysis_tasks
WHERE status = 'failed'
ORDER BY created_at DESC;

-- 某个任务对应的报告（雷达分 + 各维度 JSON）
SELECT id, task_id, radar_scores, moderation_status, created_at
FROM reports
WHERE task_id = '<ULID任务ID>';

-- 任务 + 报告联查（看哪些任务已出报告）
SELECT t.id AS task_id, t.status, t.created_at,
       r.id AS report_id, r.radar_scores
FROM analysis_tasks t
LEFT JOIN reports r ON r.task_id = t.id
ORDER BY t.created_at DESC
LIMIT 20;

-- 最近的预约（name 明文，phone 密文）
SELECT id, user_id, task_id, name, store_code,
       status, source, appointment_at, created_at
FROM bookings
ORDER BY created_at DESC
LIMIT 20;

-- 某用户的完整链路：照片 → 任务 → 报告 → 预约
SELECT * FROM photos          WHERE user_id = <用户ID>;
SELECT * FROM analysis_tasks  WHERE user_id = <用户ID>;
SELECT * FROM bookings        WHERE user_id = <用户ID>;

-- 审计日志（按动作类型过滤）
SELECT id, actor_id, actor_ip, action, target_type, target_id, created_at
FROM audit_logs
ORDER BY created_at DESC
LIMIT 50;
```

> 提示：`reports` 表的 `stype/style/subzone/struct_/radar_scores/extra` 都是 **JSON 列**，
> Workbench 里点开单元格能看完整内容；也可用 `JSON_EXTRACT(radar_scores, '$.stype')` 取某个值。

## 6. 典型排查场景

> 思路统一：**先在 MySQL 顺着 `analysis_tasks.status` 定位卡在哪一步，再结合 Redis / 日志看细节。**
> 任务链路：照片 `photos` → 任务 `analysis_tasks` → 报告 `reports`。

### 场景 A：某次分析失败了，想知道原因

```sql
-- 1) 先看这个任务的状态和错误码
SELECT id, status, llm_provider, error_code, error_message,
       photo_id, started_at, finished_at, created_at
FROM analysis_tasks
WHERE id = '<ULID任务ID>';
```

按 `status` 判断：
- `failed` → 直接看 `error_code` / `error_message`，这就是失败原因（如 LLM 超时、返回格式错）。
- `moderated_out` → 是**照片审核没过**，转去看照片：
  ```sql
  SELECT id, moderation_status, moderation_raw, created_at
  FROM photos WHERE id = <上面的 photo_id>;
  ```
  `moderation_status = rejected`，`moderation_raw`(JSON) 里是审核返回的明细。
- `queued` / `streaming` 一直不变 → 见场景 B（卡住没跑完）。
- `done` 但用户说没看到报告 → 见场景 C。

结合日志：用任务 ID 在 `logs/api.log` 里搜，能看到该次分析的完整流水（LLM 请求/响应、报错栈）。

### 场景 B：上传后一直转圈，任务不出结果

```sql
-- 看任务是不是卡在 queued / streaming
SELECT id, status, llm_provider, started_at, finished_at, created_at
FROM analysis_tasks
WHERE status IN ('queued', 'streaming')
ORDER BY created_at DESC;
```

- `started_at` 为空且一直 `queued` → 任务根本没被处理，检查 API 进程 / LLM provider 配置（`config/dev.env` 的 `LLM_PROVIDER`）。
- `streaming` 很久没到 `done` → LLM 那边在长时间生成（prod 常见），或流中断。看 `logs/api.log` 里该任务 ID 的最后一条日志。
- 对应有没有报告：
  ```sql
  SELECT * FROM reports WHERE task_id = '<ULID任务ID>';
  ```
  没有行 = 报告还没落库（任务没成功走完）。

### 场景 C：任务显示 done，但页面看不到报告

```sql
-- done 的任务应当有且仅有一条 report（reports.task_id 唯一）
SELECT t.id AS task_id, t.status,
       r.id AS report_id, r.moderation_status, r.created_at
FROM analysis_tasks t
LEFT JOIN reports r ON r.task_id = t.id
WHERE t.id = '<ULID任务ID>';
```

- `report_id` 为空 → 任务标 done 但报告没落库，属异常，查日志。
- `moderation_status = rejected` → 报告内容被审核拦了，前端不展示。
- 都正常但前端不显示 → 是前端/接口问题，不在数据库层，看浏览器 Network 里 `/api/reports/<id>` 的返回。

### 场景 D：报告内容 / 雷达分看着不对

```sql
SELECT task_id, schema_version, radar_scores,
       stype, style, subzone, struct_, extra
FROM reports
WHERE task_id = '<ULID任务ID>';
```

- `radar_scores`(JSON) 是 4 维分数；`stype/style/subzone/struct_` 各维度明细 JSON。
- Workbench 双击 JSON 单元格看全文；或取单值：
  ```sql
  SELECT JSON_EXTRACT(radar_scores, '$.stype') AS stype_score
  FROM reports WHERE task_id = '<ULID任务ID>';
  ```
- `extra` 为 `{}` 是正常的——只有同步契约(qwen-sync)的富字段才会填，SSE 流式 provider 不产出。

### 场景 E：预约没进来 / 想看某人的预约

```sql
-- 最近预约（name 明文可看，phone 是密文）
SELECT id, user_id, task_id, name, store_code,
       status, source, appointment_at, created_at
FROM bookings
ORDER BY created_at DESC
LIMIT 20;
```

- 查不到 → 预约请求没成功落库，看 API 日志里 `/api/bookings` 的报错。
- 想追这条预约来自哪次分析 → 用 `task_id` 回查 `analysis_tasks` / `reports`。

### 场景 F：验证码相关（走 Redis，不在 MySQL）

验证码不落 MySQL，全在 Redis + 日志，见本文 **第 3 节**：
- `KEYS sms:*` 看有没有发码、`GET sms:code:*` 取码、`TTL sms:send:*` 看 60s 锁。
- 或直接在 API 窗口 / `logs/api.log` 搜 `[MOCK SMS] code=`。

## 附：账号密码速查

| 服务 | Host | Port | 账号 | 密码 | 库 |
|---|---|---|---|---|---|
| MySQL（普通） | 127.0.0.1 | 3306 | venus | devpass | venus |
| MySQL（root） | 127.0.0.1 | 3306 | root | devroot | 全部 |
| Redis | 127.0.0.1 | 6379 | — | 无 | 0 |

> 以上均为**本地开发**默认值，仅用于 dev 环境，切勿用于生产。
